## 作ったもの

[ゼロ請求書]({site}) は、フリーランス・個人事業主向けの請求書ツールです。

- 請求書・見積書・納品書・領収書
- インボイス制度（適格請求書）対応: 登録番号のチェックデジット検証、税率ごとの合計と消費税額
- 源泉徴収税額の自動計算、領収書の収入印紙額の表示
- 登録不要。データはブラウザの localStorage のみ

特徴は **「アプリ本体にサーバーが一切ない」** ことです。それでいて有料版（買い切り）の販売とライセンス発行は完全に自動化しています。

## 全体構成

```
[ブラウザ] 静的サイト（GitHub Pages）
   ├─ 書類データ: localStorage
   ├─ PDF: window.print()（ブラウザの「PDFに保存」）
   └─ ライセンス検証: WebCrypto Ed25519（公開鍵は config.js に埋め込み）

[購入] Stripe Payment Link
   └─ 決済完了 → /thanks/?session_id={CHECKOUT_SESSION_ID} にリダイレクト

[発行] Cloudflare Worker（DBなし）
   └─ session_id を受け取り → Stripe API で Checkout Session を取得
      → paid / 金額 / Payment Link ID を確認 → Ed25519 で署名したキーを返す
```

サーバー側に保存する状態はゼロ。Worker が受け取るのは Stripe の session_id だけで、請求書の中身は一切ネットワークに出ません。

## 税計算: 端数処理は「請求書×税率ごとに1回」

インボイス制度では、消費税額の端数処理は1つの適格請求書につき税率ごとに1回と定められています。品目ごとに税額を出して丸めてから合計すると、この要件から外れます。

```js
// 税率ごとに税抜合計を集計してから、1回だけ丸める
for (const [rate, { sum }] of Object.entries(byRate)) {
  const tax = roundYen((sum * rate) / 100, rounding); // floor / round / ceil
}
```

浮動小数点の誤差（例: `0.1 * 3`）で1円ずれるのを避けるため、丸める前に微小な誤差を吸収しています。税計算はすべて依存なしの純粋関数にして、`node --test` でテストしています。

### 源泉徴収

報酬・料金の源泉徴収は、100万円以下の部分が10.21%、超える部分が20.42%（復興特別所得税込み）。整数演算で計算します。

```js
export function withholdingTax(base) {
  const b = Math.max(0, Math.floor(Number(base) || 0));
  if (b <= 1_000_000) return Math.floor((b * 1021) / 10000);
  return Math.floor(((b - 1_000_000) * 2042) / 10000) + 102_100;
}
```

「手取りで○円欲しい」から額面を出す逆算は、閉じた式で近似してから前後を探索して、手取りが目標以上になる最小の額面を返しています。

### 登録番号のチェックデジット

適格請求書発行事業者の登録番号は「T + 13桁」で、13桁部分は法人番号と同じ形式で、先頭1桁が残り12桁から計算されるチェックデジットなので、打ち間違いの多くをオフラインで検出できます。ただし「実際に登録されているか」は国税庁の公表サイトで確認する必要があり、利用規約でもそう明記しています。

## ライセンス: Ed25519 署名 + 決定的発行

キーの形式はこうです。

```
ZI1.<base64url(payload JSON)>.<base64url(Ed25519 署名)>
payload = { v:1, sub:<email>, plan:"pro", iat:<Checkout Session の created>, sid:<session id の短いハッシュ> }
```

ポイントは **Ed25519 の署名が決定的** なこと。payload を session から決定的に組み立てれば（`iat` に現在時刻ではなく session の作成時刻を使う）、同じ session_id で何度 claim しても同じキーが返ります。これで

- 「発行済みキー」を保存する DB が要らない
- 購入者がキーをなくしても、サンクスページを開き直せば同じキーが出る

が両立します。

ブラウザ側は WebCrypto の Ed25519 で検証し、未対応ブラウザでは同梱の軽量ライブラリにフォールバックしています。

### Worker で確認していること

- `payment_status === "paid"`
- `amount_total` が期待金額と一致（別商品の決済で発行されるのを防ぐ）
- （任意）`payment_link` が期待する Payment Link ID と一致
- CORS は自サイトのオリジンのみ許可
- Stripe キーは「Checkout Sessions 読み取り」だけの**制限付きキー**

## 割り切ったこと（正直に）

- **クライアント側で検証するので、コードを改変すれば回避はできます。** 1,480円の買い切りで、回避の手間より払うほうが安いという前提の割り切りです。
- 失効リストがないので、返金後にキーを無効化できません。
- データは端末のブラウザにしかないので、同期はJSONバックアップによる手動移行です。

そのかわり、ランニングコストはほぼゼロ、個人情報を預からない、障害点も少ない、という利点があります。

## まとめ

「データを預からない」「状態を持たない」設計にすると、個人開発でも決済込みのプロダクトを運用負荷ほぼゼロで出せます。同じ構成は、ほかの業務ツールにもそのまま使えると思います。

## 8. やらないこと（ガイドライン）

- 偽のレビュー・体験談・利用者数の掲載、サクラ投稿、別アカウントでの推薦
- 無関係なスレッドやハッシュタグへのリンク連投、DM の一斉送信
- 他社サービスの名指し比較・誹謗（LP の比較表も「一般的なクラウド会計」に留める）
- 根拠のない数字（「〇万人が利用」「作業時間〇%削減」など）
- 税務上の断定（「これで税務調査も安心」など）。常に「一般的なルールに基づく計算で、税務上の助言ではない」と添える

コミュニティでは「困っている人の質問に答える」「作り方や失敗を共有する」ことを主にし、宣伝はその結果として興味を持ってもらう、の順番を守る。
